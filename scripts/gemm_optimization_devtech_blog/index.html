Executive summary

先说结论：GEMM 优化是一条“让数据越来越近”的路线

一次 FP32 FMA 只做两次浮点运算，却需要三个输入操作数。如果 A、B 每参与一次乘加都要从全局显存重新读取，CUDA Core 再多也只能等数据。整套优化的主线，是把可复用数据逐层搬近计算单元，并让搬运与计算在时间上重叠。

空间复用

Global → SMEM → Register

block tile 复用全局数据，thread tile 再复用 shared-memory 数据。

指令效率

float4 + Swizzle

用 128-bit load/store 减少指令，并调整线程映射避免 bank conflict。

时间重叠

LDG/LDS Prefetch

计算 block[k] 时预取 block[k+1]，隐藏 long 与 short scoreboard。

这不是 Tensor Core 教程

PDF 标题明确是 “with CUDA Cores”。实验使用 FP32 SIMT FMA，比较对象也是 SGEMM。这里讨论的 tiling、访存与流水线思想同样影响 Tensor Core kernel，但本文数字不能当作 Tensor Core 吞吐。

01 · Mental model

先建立 GPU 心智模型：算术不是唯一瓶颈

本节核心问题：一个 warp 为什么会停下来？哪些存储层级决定了 GEMM 的速度？

GPU 以 32 个线程组成一个 warp，同一 warp 执行同一条指令。当指令取数未完成、前一条指令结果尚未就绪或遇到同步屏障时，warp 会 stall；调度器只能切换到另一个 ready warp。增加并发 warp 可以隐藏一部分延迟，但不能修复低效的内存访问模式。

Global memory：看 coalescing

一个 warp 访问连续地址时，硬件可用尽量少的 32-byte sector 满足请求；地址分散会把一次理想访问膨胀成多次事务。

Shared memory：看 bank conflict

32 个 bank 对应连续的 32-bit word。多个线程同一阶段命中同一 bank 时，请求会被重放；padding 与 swizzle 是常见解法。

Roofline 给出的第一条诊断线索

算术强度Arithmetic Intensity = 2 × M × N × K ÷ Bytes

分子是 GEMM 的 FMA 工作量，分母是观测存储层级上的数据传输量。算术强度低时，性能被带宽上限约束；通过 tiling 增加复用后，kernel 才可能向计算上限移动。PDF 第 14 页以 Nsight Compute Roofline 作为后续优化的分析入口。

02 · Baseline

基线为什么慢：每个线程只算一个 C 元素

本节核心问题：三重循环看起来已经完全并行，为什么只有 1.861 TFLOP/s？

矩阵M=N=4096，K=2048
表达式C = A × B
平台A100 PCIe 40GB
软件CUDA 11.1
时钟mclk 1215 / pclk 765 MHz
测量100 warmup + 100 iterations
// 一个线程对应 C[i][j]
for (int k = 0; k < K; ++k) {
    C[i][j] += A[i][k] * B[k][j];
}

block 为 32×32，grid 为 128×128。问题不在并行任务数量，而在每个线程都沿 K 维反复访问全局显存：同一 A 或 B 元素会被相邻线程重复读取，warp 频繁等待 memory dependency。实测结果是 1,861.22 GFLOP/s、36.922 ms，只达到实验时钟下计算上限的 17.63%。

更多线程不能补偿重复搬运

如果每次 FMA 都伴随高延迟 load，增加线程只会让更多 warp 一起排队。第一步应提高数据复用，而不是继续放大 grid。

03 · Stage 1

构造数据复用：从 block tile 到 thread tile

本节核心问题：怎样让同一个 A/B 元素服务更多次 FMA，同时控制 shared-memory 指令数量？

第一步：block tile，把 A/B 搬进 shared memory

每个 block 先协作加载 A 与 B 的 32×32 子块，再在 shared memory 上完成内积。全局显存访问被 block 内线程摊薄，性能从 1.861 升到 2.863 TFLOP/s，加速 1.54×。但每个线程仍只生成一个 C 元素，shared-memory load 过密，Nsight Compute 指向 Stall MIO Throttle。

第二步：thread tile，让一个线程生成一小块 C

把 C 的 block tile 放大到 128×128。初版使用 32×32 线程，每个线程在寄存器中累积 4×4 个 C 元素：A/B 搬运量增加 4×，FMA 数却增加 16×。结果跃升到 7.990 TFLOP/s，是基线的 4.29×。

继续把 thread tile 调成 8×4、16×4，分别达到 8.432 与 8.643 TFLOP/s。更大的寄存器 tile 提高了 O(M×N) 计算对 O(M+N) 输入的复用，但不能无限增大：寄存器与 shared memory 用量会限制每个 SM 同时驻留的 block。

第三步：outer product、float4 与 thread swizzle

将循环重排为 accumulated outer product：每次从 shared memory 读取一列 A 和一行 B，在寄存器中更新一个小矩阵。其价值不仅是复用，也在于拉长 LDS 与依赖 FMA 之间的距离；材料中的 profile 将 short-scoreboard stall 从约 4 cycle 降到 0.14 cycle。

随后用 float4 把四条 32-bit 指令折叠为一条 128-bit LDG/LDS/STG，并重排 thread id，让向量化访存保持 coalesced、尽量避开 shared-memory bank conflict。最终 Stage 1 达到 9.160 TFLOP/s、7.502 ms。

04 · Stage 2

隐藏流水线停顿：计算当前块，预取下一块

本节核心问题：数据复用已经做好，为什么 warp 仍在等 LDG、LDS 和同步屏障？

Stage 1 的主循环仍按 LDG → STS → LDS → FMA 串行推进。STS 必须等 LDG 完成，造成 long scoreboard；FMA 紧跟依赖的 LDS，造成 short scoreboard。软件流水线的核心不是减少工作量，而是改变工作顺序。

时间 →第 k 次迭代第 k+1 次迭代
全局预取LDG block[k+1]LDG block[k+2]
Shared 写入STS block[k+1]STS block[k+2]
当前计算LDS + FMA block[k]LDS + FMA block[k+1]

把 LDG 提前到前一轮，在其等待期间执行当前 block 的 LDS/FMA；数据就绪后再 STS。

01

Global prefetch：消除 long scoreboard

把 LDG-STS-FMA 重排为 LDG-FMA-STS。预取 block[k+1] 到寄存器，同时计算 block[k]。long-scoreboard 指标从 0.97 降到 0，性能从 9.160 升到 9.721 TFLOP/s，约 +6.1%。

02

Shared-memory double buffer：少一次 barrier，却没有更快

两个 SMEM buffer 解除 LDS[k] 与 STS[k+1] 的覆盖冲突，从主循环移除一个 __syncthreads()。barrier stall 从 0.27 降到 0.18，但性能微降至 9.705 TFLOP/s（0.998×）。

03

Shared prefetch：重叠 LDS 与 FMA

提前把下一组 shared-memory 数据读入寄存器，在当前 FMA 之间穿插 LDS。short scoreboard 从 0.07 降到 0，性能回升到 9.770 TFLOP/s。

最值得复用的经验：指标改善不等于端到端变快

Double buffer 的确减少了 barrier stall，却增加了 shared-memory 占用并改变调度条件，最终吞吐略降。每一步都必须用 kernel time 和 FLOP/s 验收，不能只看单个 stall 指标。

05 · Split-K

Split‑K：用更多 CTA 换取一次额外归约

本节核心问题：当 M、N 产生的 CTA 不足以填满 108 个 SM 时，如何继续提高并行度？

A100 有 108 个 SM，材料以每 SM 约 2 个 block 作为充分占用的经验目标，即至少需要 216 个 CTA。若 M、N 较小，输出 tile 数不足，可以沿 K 维切成 s 份：多个 CTA 分别计算同一 C tile 的 partial sum，最后再归约。

A₀ × B₀A₁ × B₁A₂ × B₂
↘↓↙
C tileatomic reduction of partial sums

第一版为什么更慢？

直接用标量 atomicAdd 替代向量化 STG，无法使用 float4。实际 global sector 从理想的 65,536 增到 262,144，正好 4×，性能降到 9.674 TFLOP/s，低于不切 K 的 9.770。

先在 shared memory 中重排，再做原子归约

优化版先用 STS.128 把线程分散的 C 子块整理成连续布局，再由适合连续访问的线程映射执行 LDS + atomicAdd。性能提高到 10.041 TFLOP/s；经过 padding、按 warp 重组 shared-memory layout 与循环形式调整，最终达到 10.144 TFLOP/s、6.775 ms。

在固定 M=N=4096 时，K 越大，主循环越长，额外归约越容易被摊薄。但这不是普遍单调规律：固定 K=2048 改变 M、N 后，Split‑K 的速度比从 0.98× 到 1.18× 都可能出现。Split‑K 是 shape-specific 的配置，不是全局开关。

材料对最终增益保持了正确的谨慎

PDF 第 95 页明确写道，最终 Split‑K 提升的完整原因尚未确认，可能与更多 block 让 main loop、prolog、epilog 更好重叠有关。本文保留这一不确定性，不把相关性包装成已证明的因果机制。

06 · Library baselines

距离 cuBLAS 还差什么：最后 1.77% 最难

本节核心问题：自研 kernel 已达到 95.92% SOL，为什么 cuBLAS 仍然更快？

自研 Split‑K10.144TFLOP/s · 6.775 ms
CUTLASS Split‑K=29.981TFLOP/s · 6.885 ms
cuBLAS10.326TFLOP/s · 6.655 ms

按主实验 shape，自研实现达到 cuBLAS 的 98.23%，并略高于材料中的 CUTLASS 配置。但库实现还在几个更细层次占优：

  • 按 shape 选择 kernel：cuBLAS 会随 K 改变 128×64、128×128、128×32 等 tile，而不是用一个 kernel 覆盖所有形状。
  • 寄存器复用控制：SASS 中更积极使用 .reuse，减少 operand collector 与 register-file 带宽压力。
  • 寄存器 bank 映射：精心排列累加器与 FMA 顺序，减少 RF bank conflict 和等待组。
  • CTA remapping：调整 CTA id 访问顺序，提高跨 block 的 L2 命中率，减少 DRAM 流量。

材料提出的后续方向包括 LDGSTS、三阶段流水线、128×64 小 tile、低 shared-memory 的 Split‑K swizzle，以及 serial reduction。它们共同说明：越接近硬件上限，优化越从“算法结构”转向“指令调度与物理资源映射”。

07 · Playbook

可复用的 GEMM 调优方法：每一步都要闭环

本节核心问题：换一张 GPU、一个 shape 或一种数据类型，应该按什么顺序重新优化？

  1. 01
    固定实验与理论上限

    锁定 M/N/K、布局、数据类型、alpha/beta、GPU 时钟、warmup 与迭代次数；用实际时钟计算 SOL，别直接套规格表峰值。

  2. 02
    先查访问正确性

    验证 global coalescing、shared bank conflict、向量化对齐与边界处理。无效事务会让后续流水线优化失去意义。

  3. 03
    建立三级 tiling

    CTA tile 负责全局→SMEM 复用，warp tile 分配工作，thread tile 在寄存器中累积。逐步扩大 tile，同时监控寄存器与 occupancy。

  4. 04
    用 stall reason 决定流水线

    long scoreboard 高，优先做 global prefetch；short scoreboard 高，增加 LDS/FMA 距离或寄存器预取；barrier 高，再考虑 double buffer。

  5. 05
    并行度不足再尝试 Split‑K

    计算 CTA 数与 SM 数，评估 partial-sum reduction、memset 和非确定性代价；用 shape sweep 验证，而非只测一个 K。

  6. 06
    始终对照 cuBLAS / CUTLASS

    库性能既是上限参照，也是 tile、stage、split-K 与布局选择的提示。比较时必须保证表达式和数据布局等价。

Profile→提出单一假设→最小代码改动→检查正确性→重测 kernel time
08 · Limits

边界条件：这组 2021 年数据不能直接外推

01

固定硬件

A100 PCIe 40GB，且 pclk 固定为 765 MHz。不同架构的 RF、SMEM、cache 与调度规则都可能改变最优 tile。

02

固定精度

实验是 FP32 CUDA Core SGEMM，不覆盖 TF32、FP16/BF16 或 Tensor Core MMA。

03

友好 shape

主结果 M=N=4096、K=2048，均为 tile 的良好整数倍；边界与非对齐 shape 没有在主线展开。

04

软件较旧

基于 CUDA 11.1/11.3。编译器代码生成、cuBLAS 选择器和 CUTLASS 模板此后均已演进。

05

Split‑K 非确定

atomic reduction 的加法顺序不固定；对严格数值复现有要求时，需要改用确定性归约方案。

06

部分原因未隔离

最终 Split‑K 增益的完整来源未由实验单独证明，原材料也明确承认这一点。

Conclusion

最终结论：高性能 GEMM 是数据流设计，不是循环展开比赛

从 1.861 到 10.144 TFLOP/s 的 5.45× 提升，可以压缩成三句话：用层级 tiling 创造空间复用，用向量化与 swizzle 保持每次访问有效，用软件流水线把无法消除的延迟藏到 FMA 后面。

真正成熟的调优过程还要接受两件事：减少某项 stall 不保证 kernel 更快；某个 shape 上有效的 Split‑K 和 tile，不保证能迁移到另一个 shape。最终裁判永远是正确性、完整 profile 与可重复的端到端时间。

少搬数据 → 搬连续数据 → 提前搬数据 → 用足够计算覆盖搬运
